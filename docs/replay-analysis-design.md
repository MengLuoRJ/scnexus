# 录像库、跨场统计与分阶段深度复盘设计

## 1. 状态与本轮范围（2026-11-02）

本文区分**代码核对基线**、**本轮实施目标**和**后续设计**，不作为运行验证报告。代码基线为 `packages/replay-parser`、main 的 `modules/replay`、shared 的 `replay.type` / `replay-insights.type` 及现有 MCP 工具注册。最终交付以合并后的契约、测试和桌面实测为准。

- 已有：资料/类型隔离的本地录像库、手动索引/导入/导出/删除、SHA-256、真实 UTC 对局时间、玩家资料句柄匹配、组件 worker 解析及持久化；tracker 经济采样、生产/升级观察时间线和玩家叠加曲线。
- 用户确认本轮实现：**跨场基础统计与调用游戏观看录像**。这不是承诺本轮提供 APM、聊天或完整建造顺序；本文不将尚未验证的实现记为已交付。
- 后续推进：game/message 解码、单位生命周期/损失、交战与完整建造顺序等深度复盘，逐指标验收，不一揽子宣称“全协议支持”。
- AI 本轮**仅设计**：现有 MCP 服务已实现，但没有录像工具、复盘数据授权或内置模型调用；不能将战役操作的自动审批解释为录像数据授权。
- 自动监听/扫描/分析、云端上传、报告导出、作品归属识别不在本轮范围。已有 ZIP 导出不等于分析报告导出。

相关实现边界：[架构](./replay/replay-architecture.md)、[解析包与样本证据](./replay/replay-parser-package.md)、[数据库](./replay/replay-database.md)、[AI 授权与工具设计](./ai-assistant-design.md#录像复盘-ai-设计本轮不实现)。

## 2. 运行层次与当前事实

| 层次         | 当前实现                                                                                | 不得推导的能力                                              |
| ------------ | --------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 容器         | main 的 `utils/mpq` 只读读取，支持原始/ZLIB/BZIP2；BZIP2 使用内部 `@scnexus/bzip2-wasm` | 不支持的压缩组合不能标成协议不兼容；StormLib 不是主路径     |
| 基础索引     | user-data header 与自描述 details，读取地图、玩家、胜负、baseBuild、游戏时长、playedAt  | 不能由文件修改时间推测对局时间，不能从目录类别推测天梯/模式 |
| 显式组件解析 | initData、attributes、tracker，各自能力状态；有界 worker、hash/版本失效                 | `completed` 仅指这三类组件解码，不是完整深度复盘            |
| tracker 投影 | `tracker-insights-v1`：经济采样、实体出生、生产开始/完成、升级完成；缺值 null           | 无 APM/EPM、聊天、操作指令、损失明细或交战识别              |
| 存储         | `node:sqlite`，`replay_files` + `replay_runs`，UUID 索引及有界 JSON                     | 不是 sha256 主键；没有逐事件统计表或 gzip 文件缓存          |
| MCP          | 本机 HTTP、Token、Host/Origin 检查、查询与受控战役操作                                  | 本机服务不代表模型在本机运行；未注册录像工具                |

parser 只接受 host 提供的组件字节，不访问文件系统、MPQ、Electron 或 Vue。主进程负责文件归属与目录边界、任务预算、持久化、业务投影；renderer 通过 `ipcs/` 调用，不自行读取录像或解析协议。`node-stormlib` / `node-casclib` 是独立能力包，当前 replay 主路径没有导入，不能作为已接入的单位数据源。

`replay.header` 在 MPQ user-data 块，不是归档成员；其他已知成员按固定名称读取，不要求 listfile。官方 s2protocol 是协议定义与对拍基准，运行时不执行 Python，也不依赖第三方 TS 完整协议移植。

## 3. 协议、时间与缺失状态

### 3.1 组件级版本支持

- header/details 为自描述 Versioned；attributes 为独立格式，均须检查结构与预算，不表示所有字段语义跨版本恒定。
- initData 为 **build-specific bit-packed**，当前仅精确注册 baseBuild `70154`、`98310`；`98370` 未注册，不套用最新/相邻表。
- tracker 使用自描述 `tracker-versioned-v1`，十类稳定事件投影与正安全整数源 baseBuild 独立记录。未知事件或已知事件 schema 不匹配在完整边界可确定时跳过并诊断为 partial；截断、非法 wire、越界等不得猜边界继续。
- game/message 尚未解码；必须先引入经核对的对应 build 协议表及真实样本，才能开放相应指标。tracker 可用并不赋予 game/message 支持。
- 版本登记需固定上游 commit、来源/许可、表内容摘要、decoder/algorithm 版本与样本覆盖；禁止静默联网换协议。真实对拍与合成测试分别登记，单份样本不代表整个 build 或全部事件覆盖。

### 3.2 时间与身份

- 原始定位以 `gameLoop` 为准，当前 `loop / 16` 为游戏秒，**不是实际经过秒**。历史版本、速度、暂停等未经验证前不统一套用 22.4 loops/s；采集率保持资源/游戏分钟，不二次按 Faster 放大。
- 未来动作频率必须显式声明分母、时间窗口和速度转换版本；游戏分钟与实际分钟指标不能混用。
- 玩家身份用 details 的 toon 资料句柄精确匹配选择的资料；昵称、账号目录 ID、数组位置均不可替代。tracker `playerId`、game `userId`、details `slot` 通过明确 setup 映射，冲突/缺失保留未知。
- 观察者不计入玩家统计；不从对手结果补“我的胜负”，不将未知结果当败局或平局。

### 3.3 数据状态（后续指标契约要求）

现有组件状态为 `available / partial / missing / unsupported / corrupt`。未来指标还须区分 `not-analyzed`（未运行或缓存失效）、`not-applicable`（模式不适用），以及运行失败/取消/资源超限；这些是设计要求，不表示现有 DTO 已包含所有枚举。

每个指标返回值、单位/时间基准、来源组件/事件、状态与原因、覆盖范围、算法/游戏数据版本。缺少证据返回 null/不可用，而不是 0 或空成功；仅在所需事件覆盖完整且确实无事件时，0/空列表才代表真实零。partial 可保留有证据的观察值，但不得宣称整场完整或参与要求完整数据的聚合。采样缺口断线，不补零、不外推；缺字段不从相邻值、人口、资源差额猜测。

## 4. 本轮跨场基础统计与观看录像

### 4.1 跨场统计口径与验收

1. 范围固定为用户选定的 `ReplayScope { profileHandle, category }` 内**全部已扫描录像**，不随列表文字搜索变化；主进程再次检查当前文档根与物理目录，不跨资料收集“全账号”数据。
2. 优先复用已索引 metadata，不触发隐式深度解析。来源是本地**已索引样本**，不是完整生涯战绩或服务器天梯记录。
3. 相同非空 SHA-256 在同一统计范围只计一次；不同 hash 不凭地图/玩家/时间模糊合并。无 hash 的旧记录不能可靠去重，需明确排除数量及重索引提示。
4. 区分文件数、去重对局数、唯一匹配玩家局数、已知胜/负/平/未知结果数；胜率定义为 `胜 / (胜 + 负)`，平局与未知不进分母，并展示分母。分母为 0 显示不可用而非 0%。
5. 对种族统计仅纳入明确的 1v1，对手种族未知时不猜测；地图战绩包含团队局，但不将队伍结果解释为个人表现。趋势按真实 `playedAt` 的 **UTC 月份**分组，不按本地月份或 mtime；无日期录像只计总数，不进入月份趋势。缺失字段单独计数；时长是游戏时长，均值展示有效样本数。小样本显示局数，不输出显著性或实力因果结论。
6. `Multiplayer / Campaign / Challenge` 是目录类别，不等于 1v1/天梯/合作模式；尚未可靠识别的模式不得混称天梯胜率，不把团队胜负解释为个人表现。
7. 本轮不聚合 APM/EPM、操作水平、交战效率或完整建造顺序；已有经济采样也不自动变成跨场绩效评分。

验收覆盖重复文件、缺 hash、身份无匹配/冲突、无结果、平局、缺时间/种族/地图、空范围、资料切换与根目录变化；用可手算样本检查分子/分母/排除数量，1000×700 窗口确认统计与录像列表布局。实现若只提供上述维度的子集，应据实列出，不能由本设计宣称全部已交付。

### 4.2 调用游戏观看与验收

- 观看指交给已配置的 SC2 游戏客户端，不是内置播放器或视频导出。main 只接受范围及已索引 UUID，复查当前归属、真实路径、普通录像文件和游戏配置，拒绝任意路径/命令。
- 复用受控游戏启动服务与明确的参数数组，不拼接 shell 命令，不更改录像、不自动下载旧客户端、不绕过本地游戏操作限制。
- 游戏版本/历史录像兼容性以真实客户端为准；启动请求成功仅表示已发起，不证明已进入回放。未实测前不承诺自动选对版本、任意历史录像可看或自动跳到某一 loop。
- 无配置、文件丢失/变更、越界/符号链接、版本不匹配与进程启动失败需有可理解反馈；不把失败回退成成功提示。若只能感知进程启动而不能感知游戏拒绝，明确该可观测边界。
- 验收检查范围与参数约束、长路径/中文路径、失败反馈、真实 Windows 客户端启动与版本行为；1000×700 检查入口与忙碌状态。本轮文档工作不代替这些运行验收。

## 5. 后续分阶段深度复盘

| 阶段            | 交付前提与内容                                                      | 验收门槛                                                                                               |
| --------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| D1 协议与证据   | build-specific game/message 表、完整性诊断、用户映射、速度/时间口径 | 官方 decoder 真实样本逐事件对拍，覆盖未知 build、损坏、预算、观察者/AI/团队/离开与暂停；未覆盖明确登记 |
| D2 操作/聊天    | 动作账本、APM/EPM、聊天和控制组/选择等时间线                        | 完成下表分类规则与黄金样本；可追溯到原事件，不能仅以解码成功验收                                       |
| D3 单位/交战    | 生命周期、损失、估计交战片段、版本化游戏数据                        | tag 回收、归属/类型变化、取消/幻象/临时对象有对照用例，损失不冒充资源结算                              |
| D4 完整建造顺序 | 下令→开始→完成/取消及升级链、供应上下文                             | 成功/失败/取消/队列/变形逐例对照；无法确定关联时保留未关联，不伪称完整                                 |
| D5 深度聚合/AI  | 仅将通过验收的指标开放跨场查询和授权只读工具                        | 版本/完整性可比、授权撤销/脱敏/证据引用均验收；AI 不因接通就开放不可用指标                             |

D1–D5 是依赖关系，不是本轮承诺或日期计划。D3 的独立 tracker 生命周期工作可先推进，但没有 D1 的动作数据仍不能提供动作指标或指令型建造顺序。

### 5.1 指标所需事件与禁止推算

| 指标         | 最低来源与定义要求                                                                                                                                               | 禁止替代与缺失行为                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| APM          | game 的命令、选择、控制组等动作事件（如 SCmd/SSelectionDelta/SControlGroupUpdate，名称以实际 build 表为准），明确哪些计一次、是否计重复/自动事件、活跃时间与分母 | 不能用 tracker 数量、出生数、采样数、人口或游戏时长猜测；未支持 game 时不可用。标为“事件计数 APM”，不冒充客户端结算 APM                                |
| EPM          | APM 动作账本 + 有版本的重复/无效动作过滤窗口、目标/选择/控制组状态；保留被过滤依据                                                                               | 不等于 APM 乘固定系数；命令事件不总能证明执行成功，“有效”仅为明示启发式，不等同官方或最优操作                                                          |
| 聊天         | message 的实际聊天事件（如 SChatMessageEvent）、发送者/接收范围、时间、文本编码；标记流覆盖与观察者                                                              | ping/loading/离开等非文本事件不当聊天；缺流显示不可用，完整流且无聊天才显示“无聊天”，不补写对话                                                        |
| 操作指令     | game 的命令能力链接/索引、标志、目标点/单位、队列信息，并以 build 对应能力目录解释；选择/控制组状态按需重建                                                      | tracker 只证明实体/状态观察，不证明下令、成功或意图；未知技能保留原始 ID 与未解析状态，不猜战术                                                        |
| 损失         | tracker Born/Init/Done/Died、OwnerChange/TypeChange、setup；tag index+recycle 生命周期，死亡时类型/归属；资源价值需要对应版本/地图/mod 成本目录                  | 死亡数不直接等于战损，初始/临时/幻象/召唤/变形/取消/复活/中立需分类；不得用军队价值前后差额当损失或用当前版本价格套历史单位                            |
| 交战         | 经校验的死亡/伤亡与位置/时间，参与者及所有权；如需命令/伤害细节还要相应事件证据                                                                                  | tracker 位置是稀疏观察，通常无完整伤害/交火记录；聚类只能标“估计交战片段”并公布阈值/覆盖，不能据此编完整战斗过程或击杀归因                             |
| 完整建造顺序 | game 下令/队列/取消 + tracker 生产开始/完成、出生、变形与升级，版本化技能→实体映射及实体关联规则                                                                 | Born 是出现、Init/Done 包括折跃、Upgrade 是升级完成，均非精确下令时间；不通过固定建造耗时倒推，不把工人/初始奖励当本局新生产；只能给有证据的观察时间线 |

### 5.2 可信结果与持久化验收

- 保留原始事件序号/gameLoop、组件及源 build，投影记录 evidence 引用；算法变化或源 hash 变化必须失效/显式重算。不能因路径相同复用旧结果。
- 游戏数据目录必须注明来源、许可、build/mod 与可信范围；CASC 能力包存在不等于数据已接入。自定义地图未知成本/能力时对应语义不可用，原始事实仍可查看。
- 保持有界 worker 和读取/事件/输出预算；资源超限、失败/取消不产生“完整”缓存。事件明细扩展后再评估表/文件缓存，不能把设计中的存储路径当现有实现。
- 解码验收（官方对拍）、业务验收（人工可核对黄金样本）、持久化/hash 失效验收及 UI 验收分别记录。测试跳过、仅合成数据或单个 build 样本不构成全面覆盖。
- 深度界面在 1000×700 使用受控滚动、分页/抽样和证据定位；所有语言同步。空值/partial 与真实零不同，图表不隐藏未知区间。

## 6. 待决策与非目标

- APM 动作白名单、EPM 过滤算法/窗口、离开/暂停时分母及历史速度映射，需要真实样本确认后版本化，本文不预填“标准数值”。
- 游戏数据来源与历史 build/mod 覆盖、实体命令关联置信条件、交战聚类阈值和损失定价口径尚待验证；不以看似合理的估算替代缺证据。
- 大库分页/虚拟列表、批量分析任务进度/取消、作品归属、报告导出与自动监听另行评估；地图名称相同不足以证明本地作品归属。
- AI 的授权生命周期、脱敏别名、分页/时间窗预算及外部发送确认界面见 AI 文档，实施前仍需产品与隐私验收。
- 不做录像修改、版本转换、账号云同步、社区比较或第三方后台上传。本地已有数据不能证明玩家操作意图、失误原因或胜负因果。
