# 录像库与复盘分析设计（提案）

## 1. 范围与状态

本文是提案，不含实现代码，也未新增依赖。目标是给出录像（`.SC2Replay`）工具链调研结论、可复用组件判断，以及与 SCNexus 现有能力结合的分阶段方案。

按 [开发规范](../AGENTS.md) 约定，文中"建议""目标""待决策"均表示后续实施约定，不代表已完成；实际依赖版本与运行能力以各包 manifest、锁文件和实测为准。

## 2. 调研：现有工具链

### 2.1 解析层

| 项目 | 语言/许可 | 定位 | 结论 |
| --- | --- | --- | --- |
| Blizzard `s2protocol` | Python / MIT | 官方参考实现，按游戏 build 生成协议定义 | 唯一的稳定真源；不直接用于本应用运行时 |
| `sc2reader` | Python / MIT | 高层语义（Player/Unit/Team 对象、APM、选择、建造插件） | 语义与字段命名的最佳参考；不复制其运行时代码 |
| `Scelight` / `icza` 的 MPQ 与 s2prot | Java / 开源 | 桌面级回放分析，含 MPQ、协议、图表 | 历史上最完整的本地实现；架构参考价值大于代码复用价值 |
| `icza/mpq`、`icza/s2prot` | Go / MIT | MPQ + 协议 | 可读性好的移植参考 |
| `mpyq` | Python | 最小 MPQ 读取 | MPQ 层在本项目已由 StormLib 解决 |
| `sc2ts`、`s2protocol-ts` | TypeScript / MIT | npm 上的 TS 移植，自带 MPQ 与 CLI | 可用性未经验证（偏 Bun、维护者单一、协议覆盖需核对）；不宜作为核心依赖 |

结论：JavaScript/TypeScript 侧没有权威且长期维护的完整实现。**协议定义必须自己从官方仓库派生并随补丁更新**，运行时用一个通用解码器承载，不绑定第三方移植。

补充两点事实，它们决定了架构分层：

- `replay.details`、`replay.initData` 使用**自带类型信息的 versioned 解码**，因此基础信息可以在不匹配具体 build 协议的情况下解出。
- `replay.game.events`、`replay.tracker.events` 使用**按 build 生成的 bit-packed 协议**，必须匹配 `m_baseBuild`，否则只能整体放弃深度分析。

### 2.2 产品层

| 工具 | 形态 | 能力 | 缺口 |
| --- | --- | --- | --- |
| Sc2gears | Java 桌面（已停更） | 回放库管理、批量统计、自动保存 | 32 位 Java 依赖、界面与语言过时 |
| Scelight | Java 桌面（开源） | 深度统计、图表、可扩展 API | 同样受 JVM 与停更限制 |
| SC2ReplayStats | 云端 + 上传器 | 目录监控自动上传、时间线、建造顺序、经济、单位交易、地图/对局战绩（2026 仍在迭代） | 数据必须上传到第三方；无本地内容关联 |
| SpawningTool | 云端 | 建造顺序库与构建对照 | 只做建造，不做整场复盘 |
| starcraft2.ai / rtsbase | 浏览器上传 | 单场复盘 + AI 教练，UI 已按"总览/单位/表现/建造/交战/宏观"分栏 | 必须上传；无本地库概念 |
| SC2 Pulse | 云端 | 天梯 MMR、段位、比赛历史 | 只提供账号维度数据，不解析回放 |

共性缺口有三处，正好是 SCNexus 的落点：

1. **本地优先**：不上传即可获得完整复盘，上传是可选出口而非前提。
2. **与本地内容关联**：地图/战役/自制作品与对局的双向关联，现有工具都不做。
3. **中文与国服场景**：界面、地图名、玩家名与国服对局习惯。

### 2.3 本仓库已具备的可复用件

| 组件 | 位置 | 作用 |
| --- | --- | --- |
| `@scnexus/node-stormlib` | `packages/node-stormlib` | worker 化的 MPQ 读取，支持 zlib/bzip2/pkware/lzma/sparse，`Archive.readFile(path, { maxBytes })` 直接取内存 Buffer |
| `utils/mpq` | `packages/app-main/src/utils/mpq` | 纯 TS MPQ，但只支持 ZLIB；不覆盖回放常见的 bzip2 段，不作为主路径 |
| `@scnexus/node-casclib` | `packages/node-casclib` | 读本地游戏数据，可取得单位/技能/科技目录，避免把造价与名称硬编码进代码 |
| AI 助手 MCP | `packages/app-main/src/modules/ai-assistant` | 本地 MCP、Token、Host 校验、逐工具授权、审计记录；复盘教练的现成出口 |
| 内容包体系 | `modules/content-package`、`campaign`、`customize`、`workshop` | 本地地图资源清单，回放与作品归属的依据 |
| 任务进度契约 | `InstallProgress` + `taskId` 事件 | 批量解析进度与取消的现成模式 |

回放是 MPQ 归档，内部文件名固定（`replay.details`、`replay.initData`、`replay.game.events`、`replay.message.events`、`replay.tracker.events`、`replay.attributes.events`），**不需要 listfile**，StormLib 按名读取即可。

一个已实测确认的例外：`replay.header` **不是归档内的文件**，而是存放在 MPQ 的 user data 块中（文件头 `MPQ\x1b`、16 字节 user data 头、随后的 user data 正文）。当前 `node-stormlib` 的 `readFile('replay.header')` 会返回 StormLib 错误 2。可行的处理是先按固定偏移读取文件头 16 字节得到 user data 大小，再解码该段；或为绑定补充 user data 读取能力。这属于阶段 0 的第一项验证，详见第 8 节。

## 3. 定位与边界

### 3.1 三类使用场景

- **对战玩家**：本地回放库 → 单场复盘（建造顺序、经济、军队、交战）→ 跨场趋势（对种族胜率、地图战绩、APM 与运营指标）。
- **内容作者**：自己的地图/战役/自制作品被玩了多少局、平均时长、胜负或通关分布、失败集中在哪个阶段。这是现有工具都没有的角度。
- **本地 AI**：通过已有 MCP 服务读取结构化对局数据，生成复盘建议，数据不出本机。

本机抽样（见第 8 节）的 6 个回放全部是街机地图，说明在有内容管理需求的用户中，自定义内容的比重可能不低于天梯。这是把"回放↔作品关联"放在阶段 3 而不是更晚的依据。

### 3.2 明确不做

- 不做录像播放器、不渲染画面、不做视频导出：播放交给游戏客户端。
- 不做账号体系、云同步与在线社区。
- 不抓取 Battle.net 页面或接口来补全数据（ToS 风险，且与本地优先原则冲突）；MMR 优先用回放自带数值，其次由用户显式提供 API Key。
- 不做回放文件修改、伪造或版本转换。

## 4. 技术方案

### 4.1 两级解析（核心决策）

| 层级 | 读取内容 | 版本依赖 | 产出 | 成本 |
| --- | --- | --- | --- | --- |
| L0 索引 | `replay.header`（user data 块）、`replay.details`、`replay.initData` | 与 build 无关（versioned 解码） | 地图、玩家、种族、队伍、胜负、时长、游戏模式（天梯/非排名/自定义/战役）、MMR（若记录）、cacheHandles | 毫秒级 |
| L1 深度 | `replay.game.events`、`replay.tracker.events`、`replay.message.events` | 必须匹配 `m_baseBuild` | APM/EPM、建造顺序、经济与军队曲线、单位生灭与损失、交战、聊天 | 百毫秒到秒级 |

这样分层的原因很直接：天梯补丁频繁（当前为 5.0.17.98310），若把基础索引绑在具体协议上，一次小版本更新就会让整个库失效。L0 保证"新补丁的回放至少能进库、能筛、能看结果"；L1 只在协议可用时提供深度分析，缺失时界面明确降级为"该版本暂不支持深度分析"，而不是报错或假装空数据。

### 4.2 解码运行时

- 从官方 `s2protocol` 派生出**紧凑的协议类型表**（JSON：事件类型 + 字段类型 + 版本标记），配一个通用 bit-packed / versioned 解码器（预计数百行），替代逐 build 生成整份代码。逐 build 生成会让产物体积失控（每个 build 的生成代码都是百 KB 级，累计可达数十 MB）。
- 类型表按 `baseBuild` **懒加载**，只随包发布一段 build 区间（建议自 4.0 起，按实际用户回放分布再调），其余版本降级。
- 协议同步做成脚本：钉住上游 commit → 生成 → 快照比对 → 人工确认，参照 `standard` 包的分发校验思路；补丁后不自动静默更新协议。
- **待决策**：自建运行时 vs 直接依赖 npm `sc2ts`/`s2protocol-ts`。倾向自建：许可清晰（MIT 定义可派生）、体积可控、可裁剪成只解码需要的字段、不受第三方维护节奏影响。

### 4.3 进程与性能

- 解码运行在 `worker_threads` 池（2–4 个，按 CPU 与内存），主进程只做调度与投影；StormLib 本身已是 worker 化，二者不冲突。这符合"高频或大体积同步操作不放在主进程事件循环"的既有约定。
- 增量扫描依据 `mtime` + `size` + 内容哈希（SHA256 复用 `hash-wasm`）：已索引且未变化的文件直接跳过，不做重复解码。
- 批量导入走队列，复用安装任务的 `taskId` + 进度事件模式（`stage`、`completed`、`failed`），支持取消；取消只停止未开始的项，已完成项保留。
- 性能基线必须在阶段 0 实测（见第 6 节），不以估算代替。目标是 L0 单场 < 5 ms、L1 单场 < 1 s（20 分钟 1v1），5000 场全量首扫控制在可接受的后台时长内。

### 4.4 存储

- 索引数据库优先使用 **`node:sqlite`**（Electron 45 内嵌 Node 24 自带），零原生依赖、无需重编译；阶段 0 若实测不可用，再评估 `better-sqlite3`，不在提案阶段先引入原生绑定。
- 表结构（初版）：`replay`（sha256 主键、路径、mtime、大小、build、地图、模式、时长、开始时间）、`replay_player`（槽位、名称、toonHandle、种族、队伍、结果、MMR、APM）、`content_link`（地图名 → 本地内容 id）、`tag`（用户标记）。
- 大对象（每分钟序列、建造顺序、聊天、单位明细）**存文件缓存**（`userData/replay/cache/<sha256>/…`，gzip JSON），数据库只存引用。不复制原始回放文件。
- 数据库带 `schemaVersion` 与迁移；缓存可随时重建，数据库不是唯一事实来源——与现有"内容库可从磁盘重建"的原则一致。

### 4.5 与本地内容的关联

- 用回放中的地图名与依赖，反查 `campaign`/`customize`/`workshop` 的已安装内容清单；命中即标记"该局来自某作品"。
- 只对**本地已安装**内容建立归属。工坊/游戏大厅中未安装的地图仅显示名称，不凭名称猜测归属。
- 作者视图按内容 id 聚合：局数、时长分布、结果分布、结束原因、参与人数。
- 战役单人/合作回放与天梯回放的语义不同（无对手 MMR、可能有存档点），聚合时分区统计，不混入同一张胜率表。

### 4.6 AI 复盘出口

在既有 MCP 服务中新增**只读**工具，沿用 Token、Host 校验、审计与逐工具授权：

- `list_replays`（按时间/地图/对局/结果筛选，默认 20、上限 100）
- `get_replay_summary`（基础信息 + 关键指标 + 相对自身历史的偏差）
- `get_replay_build_order`（按时间轴的事件列表，可按建筑/单位/科技过滤）
- `get_replay_timeline`（按分钟的供应、工人、军队价值、收入、资源结余序列）

约束：只返回投影 DTO，不返回绝对路径、原始二进制或完整事件流；回放内容作为不可信数据处理，不把其中的玩家名、聊天当成指令。教练提示词与结论留在用户自己的 AI 客户端，应用不内置模型调用。

### 4.7 互操作

- 用系统默认程序打开回放（交给游戏客户端）；提供"打开所在目录"。
- 导出：单场报告（Markdown/HTML）、批量 CSV/JSON、回放包（zip，供分享或复盘会使用）。
- 可选上传到第三方（如 SC2ReplayStats）：需要用户自带 API Key，逐次确认，不做后台静默上传；上传失败不重试到用户不知情。
- 生成分享链接类能力（drop.sc 等）先核实其公开 API 再决定，未核实前不写入方案承诺。

### 4.8 IPC 契约草案

沿用 `domain:action`、`IpcResult` 与可序列化 DTO：

| channel | 说明 |
| --- | --- |
| `replay:scan` | 扫描指定目录，返回新增/变更/丢失计数，长任务带 `taskId` |
| `replay:list` | 分页查询索引，支持筛选与排序 |
| `replay:get` | 单场详情（L0 + 已完成的分析摘要） |
| `replay:analyze` | 触发 L1 解析，可选 `taskId`，进度走事件 |
| `replay:analyze-progress` | 事件，仅发给发起调用的 renderer |
| `replay:delete` | 只从索引与缓存移除，默认不动原文件；删除文件需单独确认 |
| `replay:export` | 报告/CSV/回放包导出 |
| `replay:stats` | 汇总统计（对局矩阵、地图战绩、趋势） |

错误码按 [日志与错误规范](./logging-and-errors.md) 的既有区间顺延（`M064` 已被内容类型冲突占用，录像域自 `M065` 起，具体编号在实施时分配），覆盖：目录不可读、归档损坏、协议版本不支持、解码失败、索引损坏等，均给出可诊断原因而非空白界面。

### 4.9 界面（1000×700 基准）

- 侧栏新增"录像库"，位于内容管理与工具之间；不新增顶级导航分组。
- 列表：表格（时间 / 地图 / 对局 / 结果 / 时长 / APM），顶部筛选（种族对局、地图、结果、时间范围、模式、内容归属），支持虚拟滚动与批量操作。行不可无限高：地图名与玩家名受控换行。
- 详情：标签页——总览、建造顺序、经济与军队、单位与损失、聊天。图表与文字在同一行并排，符合标准窗口宽度约束，不在 1000px 下退化为单列。
- 汇总：对局胜率矩阵、地图战绩、时长与 APM 趋势。空数据与样本不足时明确提示，不展示误导性百分比。
- 图表方案**待决策**：手写 SVG 折线（零依赖、可控）vs Chart.js（交互省事但增包体）。倾向先手写 SVG 覆盖供应/工人/军队价值/收入四类序列，确有必要再引入图表库，并单独评审。

## 6. 风险与待决策

| 项 | 说明 | 建议 |
| --- | --- | --- |
| 协议维护成本 | 每个补丁产生新 build，需同步类型表 | 脚本化派生 + 只支持区间 + 明确降级；不做自动静默更新 |
| 第三方 TS 解析库 | 维护者单一、覆盖不全、体积不可控 | 自建通用解码器，官方仓库为唯一真源 |
| APM 口径 | 客户端记分板与事件计数结果不同 | 界面标注"事件计数 APM/EPM"，不与客户端数值混用同一标签 |
| 团队局与自定义语义 | 队伍、观战者、复活、作弊命令等差异 | 首期以 1v1 与团队局基础统计为主，深度指标先只对 1v1 承诺 |
| 隐私与 ToS | 回放含玩家名与聊天；官方数据抓取受限 | 默认纯本地、上传需逐次授权、不抓取官方站点；聊天默认折叠显示 |
| 图表依赖 | 引入图表库会增包体且改动构建 | 先手写 SVG，必要时单独评审 |
| 旧版本回放 | 老 build 未收录类型表 | 索引可用、深度不可用，错误信息说明版本而非报"文件损坏" |
| 磁盘占用 | 大库缓存膨胀 | 缓存可重建、可整体清理，按容量上限淘汰 |

## 8. 阶段 0 预验证（2026-10-31 抽样）

样本：`Documents\StarCraft II\Accounts\<账号目录>\Replays\Multiplayer` 下 6 个回放，均为街机地图。用于确认技术假设，不是功能验收。

已确认：

- `Archive.open` 与 6 个内部文件读取全部成功，含打开与关闭共 54 ms；单场约 32 KB。各文件大小：`replay.details` 1105 B、`replay.initData` 4524 B、`replay.attributes.events` 7796 B、`replay.game.events` 1466 B、`replay.tracker.events` 1977 B、`replay.message.events` 28 B。
