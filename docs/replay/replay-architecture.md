# Replay Architecture

## 1. 目标与边界

SCNexus 的录像能力应当分层落地：

- 文件管理：发现、扫描、导入、删除、打包、索引
- 解析：读取 MPQ 内部成员，抽取基本信息与事件结构
- 分析：构建时间线、经济信息、单位损失等统计
- 展示：列表、筛选、聚合、复盘界面

优先实现本地可靠性，不做云端上传/社区对比。

合作任务使用 `Coop` 虚拟分类，与 `Multiplayer` 共用游戏的实际录像目录；只有录像内容明确确认的合作录像才移入合作分类，无法识别的仍留在多人游戏。分类、索引迁移、导入校验及内容哈希／版本缓存见 [数据库设计](./replay-database.md)，分析证据及未覆盖规则见 [合作任务解析说明](../../packages/replay-parser/COOP.md)。

## 官方协议与邻近尝试

协议数据以 Blizzard/s2protocol `master` 的固定提交 `3b40c5ef01834096b4305172ef5485ec00133dcc` 为支持范围，覆盖该提交收录的全部 93 个版本；相同结构共享定义，不逐版本复制完整表（initData 17 组、game 14 组、message 5 组、tracker 3 组、header 3 组、details 7 组）。官方已知 build 精确解码，失败不使用邻近版本掩盖损坏。官方未收录 build 最多尝试三个邻近的不同结构组，必须完整消费数据且无歧义才返回候选结果，标为 `unverified`／`partial`，不宣称官方支持。

initData、game 和 message 分组件保存兼容性信息。未验证 initData 不作为自动合作分类或标准对战时长回推依据。聊天保留原始用户编号与收件人编号，经 tracker 玩家设置事件唯一映射后才显示玩家姓名；未映射的用户不按编号加一猜测。聊天文本转义显示，按页查看；所有时间仍为 16 loops/s 游戏时间。解析算法升级自动使旧分析与识别缓存失效。

## 玩家界面展示

录像详情按功能模块展示分析结果：有可用数据就显示结果，模块没有可用数据时统一显示“未能成功分析”。数值 0 是有效结果，不当作缺失；部分指标缺失使用“—”，不伪造为 0。成功解析但为空的聊天记录显示“暂无聊天记录”。没有结果的模块不显示空选择器或空表格。

协议版本回退、Tracker 字段来源、采样与插值算法、事件上限、内部 warning 和原始组件 JSON 只保留在分析 DTO、日志或开发文档，不进入玩家界面。部分可用结果仍正常显示，不用技术警告遮盖；不改变底层的兼容性判断或统计口径。生产时间线继续仅保留“开始＋完成”。

## 通用战斗指标

合作、对战及其他可解码录像共用通用指标，不以合作分类作为启用条件。界面按玩家显示指标与按单位内部类型汇总，并保留缺失／部分数据状态：

- **击杀**：以追踪死亡事件中的击杀者证据归属，属于原始击杀事件，不自动等同官方结算、敌方有效击杀或伤害。单位类型与归属变化不创造额外单位。
- **单位生成**：区分开局实体、出生、建造开始和完成；建造开始后完成不重复生产计数。召唤、建筑与变形仍需结合原始类型理解，不承诺完整指挥官专用规则。
- **APM**：命令、选择和控制组事件的原始动作频率，按游戏分钟（16 loops/s）计算，不称为官方 APM 或 EAPM。用户编号必须通过玩家设置事件映射；缺少映射、正时长或有效组件时显示未知。分母使用整个已解码 game 流观测时长，不使用最后一次动作的时间。
- **生产时间线**：详情固定显示“开始＋完成”，保留玩家选择及分页；暂不提供“仅开始”和“指令时间轴”切换。起止时间与来源分别记录：Init/Done 直接观测、Egg 完整 index/recycle 关联，以及限明确版本和标准对战证据的时长回推；时空加速须有可定位生产建筑的施放证据，成功应用与开始时间仍属推断。未知起点不使用出生时间冒充开工时间。底层指令解码、缓存与 APM 数据仍保留。界面仅展示起止时间及必要的估算标记，不显示 Tracker 来源、数据版本或时空加速诊断说明。

  时长表仅在 Blizzard 标准地图、无扩展模组、明确非合作、匹配的标准 1v1 属性和不同队伍等条件满足时启用；私人／扩展模组／合作标记不明的录像继续保留观测记录，但不套用标准时长表。历史五份公开样本中已实际验证 573 条 Egg 关联事件；协议全集支持与生产时长模型的版本适用范围分别管理；表回推及时空加速算法目前由合成测试覆盖，未宣称真实样本精度已对拍。

- **对战采样摘要**：按玩家最后一个实际计分采样展示资源余额、采集速率、当前军队价值、累计损失／摧毁军队价值，保留双方采样时间且明确不同时刻不可当作同时状态。交换比分矿气计算；分母为零、缺失或负修正时显示未知，不给出无穷或负比率，不作为 AI 战术建议。
- **完整计分曲线**：保留 PlayerStats 的 39 项字段，分为资源、收入、人口、当前投入、在建投入、活跃兵力、损失、摧毁及友伤计分。当前／在建投入属于存量，损失／摧毁属于录像累计计分，不与单位击杀数量或伤害混用；负值修正保留，缺失值不补零。所有曲线保存原始 gameLoop，以 16 loops/s 游戏时间显示，不沿用上游不同页面混用 16/22.4 的历史行为。
- **部队价值**：展示 PlayerStats 中军队矿物／瓦斯价值采样，不按单位名称猜价格，也不加入未经验证的精通、免费单位或威望折扣。缺失采样形成曲线断点，不补零。

分析算法版本变化使旧缓存失效，需要重新分析；内容哈希校验和 worker 并发边界继续沿用。自动化测试使用协议形状事件与合成二进制流，不能替代真实录像、游戏内计分板和不同版本的对拍验证。

### 可重复的本地语料验证

设置 `SCNEXUS_REPLAY_CORPUS` 为已授权的本地录像目录后，运行 `pnpm --filter @scnexus/app-main test src/modules/replay/__test__/replay-public-validation.test.ts`。该测试只读现有文件，对现代样本检查完整分析，对旧 build 62848 显式检查 partial、initData/game unsupported 及 tracker available/partial，并对所有样本检查 39 项采样及文件未被修改，不自动下载、不写数据库、不把样本纳入仓库。可额外设置 `SCNEXUS_SCORE_ORACLE=1`，逐点比较旁置的独立 `.SC2Replay.oracle.json`；没有该开关不会假装完成独立对拍。未配置语料目录时显式跳过。

## 2. 分层设计

```text
app-renderer-v2
  └─ 库列表、筛选、复盘摘要、统计面板（观看交给游戏客户端）

app-main
  ├─ replay-library 模块：目录扫描、导入/导出、索引更新
  ├─ replay-parser 调度：解析任务和回调
  └─ replay-db：本地 SQLite、缓存与索引

@scnexus/replay-parser
  ├─ file detector
  ├─ component byte contracts (MPQ I/O in app-main)
  ├─ metadata parser
  ├─ event stream parser
  └─ aggregate calculator
```

## 3. 解析器包职责

`@scnexus/replay-parser` 负责提供可重用的协议和文件分析能力，重点包括：

- `.SC2Replay` 文件识别
- 主进程提供的 MPQ 组件字节与组件清单的语义处理（不自行打开 MPQ）
- 基础 metadata 抽取
- 已实现 tracker 事件流与精确 build 的 game 指令／选择／控制组解码；message 为后续设计，尚未解码
- 统一的 `ReplayFileStatus` / `ReplaySummary`

该包不强行承诺“万能兼容所有 build”；它负责正确区分：

- `supported`
- `partial`
- `unsupported`
- `corrupt`

### 生产时间轴展示口径

详情仅保留“开始＋完成”生产时间线，按玩家切换并分页，展示实际起止时间和必要的估算标记。生产来源、数据版本和时空加速诊断仅保留在分析数据中，不在界面展开。底层命令解码继续用于原始动作指标；协议范围及未知版本策略以本文“官方协议与邻近尝试”为准。

普通训练单位通常只有 Born 事件，实际训练开始时间标记为未知，不从出兵时间减去固定训练时长倒推，也不把入队指令等同于实际开始。空的开始时间轴不表示玩家没有训练或建造。实体出现还可能来自召唤或脚本生成，不能一律称为训练完成。

## 4. 录像管理模块职责

录像管理模块应位于 app-main，职责包括：

- 指定录像目录
- 递归扫描目录下的 `.SC2Replay`
- 识别打包文件（如 `.zip` / `.7z`）并将其中的录像自动解压到目标目录
- 生成文件索引、大小、修改时间与 hash
- 删除、打包、清理和导入操作
- 与 replay-parser 协调生成分析任务

### 从详情观看录像

`ReplayAnalysisDialog` 发出 `watch` 事件，由页面通过 `ipcReplayWatch(scope, replayId)` 调用受控 `replay:watch` IPC。主进程从当前资料与类型的索引解析路径，检查目录边界、链接、扩展名及普通文件后，复用现有游戏启动器启动配置中的 SC2Switcher；renderer 不提供任意启动路径或命令参数。

录像是 SC2Switcher 的单个位置参数，不使用地图启动的 `-run`，也不使用 shell 或文件关联打开。命令行模式依据 [SC2Switcher 录像启动说明](https://gaming.stackexchange.com/a/86576)；该说明以游戏未运行为前提。启动成功只表示进程创建成功（macOS 为现有 LaunchServices 调用成功），不保证游戏已进入录像、版本资源可用或能接管已运行的游戏。解析器支持状态不限制观看。

## 5. 解析流程

```text
录像文件
  ↓
扩展名与文件头检测
  ↓
MPQ / archive component inventory
  ↓
基础 metadata 抽取
  ↓
events / tracker / message 入口识别
  ↓
summary + analysis task
```

## 6. 数据模型


## 7. 关键原则

- 让解析器首先输出“可信的基础信息”，再做高层分析。
- 对缺失字段和未知 build 的处理按组件区分：header/details、attributes 和自描述 tracker 尝试结构化解码；未知 build 不阻止已校验的 tracker 业务分析。位打包 initData/game/message 仍要求明确协议表，禁止套用最近版本。
- 本地数据库保存的是解析结果和聚合统计，上传只作为后续选项。
- 分析缓存记录每个组件的能力状态、实际 decoder 与源 build，未知事件在边界确定且字节完整时可跳过，tracker 标为 partial；已识别事件仍用于业务数据。截断、wire type 或结构损坏不得当作未知版本跳过。详情提示部分数据可能不完整，不暴露原始技术诊断。
- 分析器必须保留 `algorithmVersion` 和 `protocolVersion`，便于后续校准。

## 8. 初始执行顺序（前三项已落地，后续进度见第 10 节）

1. 先完成 `@scnexus/replay-parser` 的基础识别与 metadata 结构
2. 完成 app-main 的 replay library 目录扫描/导入/删除能力
3. 将解析任务接到主进程、本地索引和 SQLite 结构中
4. 才继续实现经济/军队/APM 曲线等高层分析

## 9. 当前已落地与使用方式

- renderer-v2 侧栏提供「录像管理」页面；进入时恢复 renderer localStorage 中最后的资料句柄及类型，仅保存这两项界面偏好。无有效历史选择或对应资料不存在时回退到第一个已识别资料，随后读取其类型目录。无资料时不扫描；存储不可用不影响选择，不进行后台监听或定时扫描。
- 设置中心保存「星际文档目录」，空值表示系统 Documents 下的 `StarCraft II`（使用系统目录 API，支持重定向的 Documents，不写死用户名）。显式识别其 `Accounts/<accountId>/<profileHandle>` 资料，界面主要展示绝对唯一的资料句柄。
- 资料句柄作为身份，账号 ID 仅作来源信息；同一文档根出现重复句柄视为歧义并拒绝，不任意选择目录。每个资料支持 `Multiplayer`（多人游戏）、`Campaign`（战役）、`Challenge`（挑战），范围固定在该资料的 `Replays/<category>`。
- 外部单个录像与压缩包均为导入复制，必须先选择资料及类型，主进程计算目标目录；不允许直接索引任意外部路径或任意安装目标。切换范围清空勾选、重复过滤及详情，防止跨资料误操作。
- 旧未归属索引保留在数据库但不提供未归属库入口；位于当前资料类型目录的旧文件在重新扫描后补齐归属并保留 UUID，不移动或删除历史文件。文档目录切换后不显示旧根下的记录。
- 「导入录像包」选择 zip/7z/rar，只读取其中 `.SC2Replay` 普通文件，放入选定资料的类型目录下独立新子目录，避免覆盖旧文件；其他附件不落盘。目标资料/类型由用户明确选择，实际路径由主进程从已识别资料计算。
- 导入拒绝不安全路径、链接、重复/大小写冲突路径，最多 2000 个录像、单个 128 MiB、总计 1 GiB；复制阶段失败清理新目录。复制成功后若索引遇到 I/O 错误，已复制录像保留以便手动重扫，不声称跨文件系统与 SQLite 的全局事务。
- 列表可按文件名、路径、地图、解码后的玩家显示名搜索。每个录像严格两行：左上地图、左下「玩家名（种族）」；右上逐玩家具名胜负（胜利 success 绿色、失败 error 红色），右下真实对局时间与紧凑详情按钮。长内容单行省略并提供完整文本提示，基础对局信息、文件路径及删除/解析操作移至详情弹窗。没有“我的账号”绑定时不推断单一视角胜败。
- 列表、详情与搜索共用玩家名显示转换：只解码一层已知实体及有效范围内的数字实体，将 SC2 `<sp/>` 转为空格，保留 `<ACNet>` 等战队标记与未知文本。不使用 HTML 渲染或通用标签剥离；既有索引立即生效，无须重新索引。
- 玩家身份从 details.m_toon 的 region/program/realm/id 生成 `profileHandle`，与当前星际资料句柄精确匹配。账号目录 ID 与角色 ID 不混用，昵称不参与匹配；匹配唯一时列表只展示该玩家胜负、详情仅加粗该玩家，无匹配或歧义时显示未知，不借用对手/电脑结果。旧索引在切换/刷新目录时重新读取以补齐身份字段。
- 对局时间读取 details.m_timeUTC（Windows FILETIME）并转换为 UTC ISO 字符串持久化，UI 按本地时间显示；不叠加 m_timeLocalOffset，不以文件修改时间代替。旧记录显示未知，手动重新索引后补齐。
- 删除必须确认，明确删除本地文件而非只移除列表。
- 使用 shared ReplayApi → preload 明确方法 → renderer `ipcs/replay` 封装。主进程验证调用来源及参数；录像模块不依赖游戏安装配置而注册。
- 主进程只读 MPQ，parser 解码 header/details，结果写入 `node:sqlite`；不会执行 Python、上传录像或计算伪造分析指标。
- 资料识别只枚举配置文档根的账户/资料目录，不进入录像、不建索引；设置中心点击识别/录像页刷新资料才执行。选择资料/类型及点击刷新会扫描对应目录，无 watcher。
- 索引流式计算 SHA-256 并检查读取前后大小/mtime/ctime；相同内容不同位置分别保留，可查询重复组，绝不自动去重删除。
- 导出根据已索引 UUID 选择 1–2000 个录像，最多 1 GiB；复制到暂存目录并验证 hash 后生成 ZIP，相同文件名加序号避免冲突。源文件缺失/变化或旧记录无 hash 时拒绝导出并提示重新索引。完整 ZIP 通过同卷硬链接发布，目标已存在时拒绝覆盖，文件系统不支持硬链接时明确失败；暂存目录清理。不复制应用数据库、分析缓存或其他私人文件。
- 新底层能力通过明确的 ReplayApi（discoverDirectories/listDuplicates/exportArchive/analyze/getAnalysis）及 renderer IPC 封装提供。

### renderer 管理与解析入口

- 对局曲线将所有已分析玩家叠加在同一图表，共享时间轴及数值刻度；玩家颜色稳定、指标线型区分，图例和点提示包含玩家身份。不同采样时间各自保留，缺失值断线、不补零；生产时间线仍按玩家切换，不影响对比曲线。

- 列表、重复组、导入、导出、删除及解析 API 必须带 `ReplayScope { profileHandle, category }`；文件/录像 ID 也由主进程验证归属与当前目录边界，不仅是 renderer 筛选。
- 「只看重复录像」按已索引 hash 查询重复组并标记各文件，不合并、不自动删除。提示用户：变更文件需重新索引后更新分组。
- 页首依次为「刷新」「导入」下拉菜单（录像文件、压缩包）与「多选导出」；保留资料和类型选择，不提供刷新资料或重复筛选按钮，也不请求重复组。页面不常驻显示说明与底部小字，保留操作失败反馈、空状态及模块级分析失败提示。
- 仅在「多选导出」模式显示勾选框、总选择数、选择可见项、清空与「导出 ZIP」；选择跨搜索保留，取消退出或切换资料/类型均清空选择并退出模式。删除或刷新后移除已不存在的 UUID。无资料或任务繁忙时禁用相关操作。
- 「导出 ZIP」使用受控的原生保存对话框（固定 ZIP 过滤器），取消不导出；仅向导出服务传入已选 UUID 和目标路径。服务仍限制 2000 个 / 1 GiB、校验源文件并拒绝覆盖已有文件；保存对话框选择已有路径不意味着服务允许覆盖。
- 「解析组件」显式启动 worker，完成后展示持久化结果；「解析详情」只调用 getAnalysis，不隐式启动分析。空结果提示尚未解析或 hash/算法版本失效，读取失败单独显示错误，不当作空结果。
- 详情面向玩家展示对局信息与模块分析结果，不显示 hash、parserVersion、baseBuild、协议/算法版本、原始组件或内部 warnings；这些信息仍可持久化用于问题排查。
- 聊天与生产记录按页展示；文本始终转义，不执行录像中的标记，也不把原始事件数组整批渲染进 DOM。
- 新 UI 使用 Nuxt UI 与 zh/en/zh-Hant 文本，在 1000×700 基准检查长路径、候选目录及详情弹窗。自动扫描、自动分析未启用；已有 tracker 经济采样与生产观察界面，不等于完整深度复盘。

- `analyze(id)` 显式触发 initData / attributes / tracker 原始结构解析，在 worker 中读取和解码；`completed` 仅代表三个组件均已解码，不代表完整录像分析。未知 baseBuild 仍可解析 attributes 与经结构校验的自描述 tracker；initData 无精确协议时标记不支持。`getAnalysis(id)` 同时检查算法版本及实际文件 hash；内容变化须先重新索引。源文件访问失败向上传递，不吞为成功。
- 主进程 MPQ 读取在分配前校验成员偏移与压缩长度不超出实际文件；表最多 1,048,576 项，自动 `(listfile)` 压缩及展开大小均限 4 MiB。通用成员默认限 512 MiB（`maxMemberBytes` 可配置）；录像读取限 32 MiB，组件再应用更小的读取限制，防止小型恶意归档声明超大缓冲区。文件源读取也在 Buffer 分配前核对实际文件范围。
- 主进程 MPQ 读取支持原始、ZLIB 和 BZIP2 单一压缩；BZIP2 使用`@scnexus/bzip2-wasm`（内部维护的官方 libbz2 WASM 构建）并严格限制输出大小、校验 CRC、拒绝尾随数据/拼接流，未支持的压缩组合明确报错。
- 本文前面的统计 schema、任务队列、播放/复盘是目标能力，尚未全部实现。当前字段以 shared `replay.type` 和实际 SQLite 表为准。

真实样本与协议边界见 [解析包文档](./replay-parser-package.md)，持久化方案见 [数据库文档](./replay-database.md)。

## 10. 设计对照与剩余计划（2026-11-02）

### 已完成的基础，不等同于全部产品目标

- 本地库：标准账户目录候选识别、手动扫描/添加、SHA-256、重复组、导入/导出 ZIP、确认删除与 SQLite 索引。
- metadata：地图、版本/baseBuild、游戏时长、真实 UTC 对局时间、玩家/种族/队伍/胜负；旧索引须手动重扫补齐新字段。
- 协议基础：header/details、attributes、自描述 Versioned 与 bit-packed 解码器；按官方全集注册 initData，tracker 独立采用 `tracker-versioned-v1` 十类稳定事件投影。
- 运行与界面：有界 worker、结果版本戳/hash 失效、原始组件持久化、候选目录/重复筛选/导出/显式解析、两行列表及详情弹窗。

### 本轮目标与后续设计

用户确认本轮实现跨场基础统计与调用游戏观看录像，深度解析后续推进，AI 本轮仅设计。以下目标不代表已验收。统计口径：当前档案/当前分类全部已扫描录像，不随文字搜索变化；按 contentHash 去重；胜率 win/(win+loss)，draw/unknown 单列；对种族仅明确 1v1，地图战绩含团队；趋势按真实 playedAt 的 UTC 月份，无日期只计总数。完整规则及验收见 [分阶段复盘设计](../replay-analysis-design.md)。
